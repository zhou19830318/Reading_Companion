## 1. 结论摘要

1. **总体可行,且起点高于 v4.0 的假设。** v4.0 §8.2 的 Phase 0(硬件与基础工程验证)与 Phase 1 的大部分(纯阅读、传书、书签、中文排版)在当前固件中已实现并经过设备验证;AI 语音往返(STT → OpenClaw → 屏显回复)也已端到端打通。估算总人天从 v4.0 的 ~66–100 天下调到 **~38–52 天**,重心后移到**可靠性(FR-01)、本地数据层(RH/RP)与协议隔离(Bridge)**。
2. **最大的风险不是功能,而是约束**:Flash 88.3%(OTA 双槽余量仅 ~0.76 MB)、WiFi 上行后内部堆 Free ~7.3 KB(2026-09-28 实测)。v4.0 §8.3 的「新增功能 RAM < 40 KB」预算必须按 **PSRAM-first** 解释,任何内部 DRAM 新增 > 2 KB 的设计都要单独过会。
3. **v4.0 与项目 SCOPE.md 有 4 处冲突**,已在第 4 章逐条裁定;裁定原则:v4.0 的产品目标优先,但沿用 SCOPE 的理由边界(打字输入差 → 不做打字笔记,做语音笔记)。
4. **一个 v4.0 未覆盖、但当前已暴露的问题**(e-ink 被网关心跳帧反复刷新)列入 M0 高优先修复,否则电量与残影验收(§9 性能指标)不成立。

### 3.4 本轮设备验证新发现(2026-09-28,工具轮复现)

`CMD:GO_VOICE` + `CMD:VOICE_TX 帮我定一个明早8点的闹钟`,完整日志 `/tmp/voice_tx3.log`:

1. **§11.3「卡在等待回复」修复验证通过,关闭**:工具轮 10.6 s 全链路成功(`chat.send id 1` → thinking 流 → `tool: automations start/result` → cron job added → chat delta/final → `reply: 搞定!⏰ 明早 8:00 会叫你起床。`)。网关在工具执行期间持续发送 `thinking`/`status`/`tool` 帧,最长静默 ~4 s,远低于 120 s 静默超时 → **不需要**实现「超时后迟到 final 仍接收」(§11.5-2 撤销)。
2. **新 bug A(高优)**:网关 `tick`(30 s)/`health`(30 s 错相)等非聊天帧每次到达都触发一次 e-ink fast refresh(日志中每个 `WS text (…tick…)` 后跟 `GFX Time = 16-18 ms` → 597 ms 刷新)。空闲 30 分钟 = ~120 次全屏刷新:耗电、残影、且 **mEM 心跳被淹没**。修复方向:`OpenClawSession` 对 event 类型分类,`tick`/`health`/`sessions.changed` 等静默吞掉不通知 UI;仅 `chat`/`agent error` 上抛。
3. **新 bug B(中优)**:最终回复以裸文本渲染,markdown 符号直接上屏(`**8:00**`)。M0 做最小修复(剥 `**`/`*`/反引号包裹符);完整的 Markdown 子集渲染与 AI-01 一起做。
4. **观察项(硬件侧,非固件)**:两次「设备从 USB 消失」均发生在 WiFi 连接瞬间,5 s 内自动重新枚举、无 panic dump、无 crash_report → 判定为 USB 供电/线缆瞬断而非固件崩溃。**但**注意:两次复现都在同一位置,不排除 WiFi 上电浪涌触发;建议用户换短线/带屏蔽线缆或带供电的 hub 复测一次,结果记入进度表。

### 3.5 B2:WiFi 连接瞬间三次同签名 panic —— 根因与 F2 修复(2026-09-29)

**症状(三次完全同签名)**:Load access fault(`MCAUSE=5`),`MEPC=0x420e6e1e` = `pthread_mutex_lock_internal` 的 `lw a4,4(a0)`(读 `esp_pthread_mutex_t::type`,结构 `{sem@0, type@4}`,`pthread.c:56-63`),`RA` = `pthread_mutex_destroy`;均在 WiFi 连接、内部堆 2–5 KB 时发生。j.log panic 瞬间 `Free:194 / MaxAlloc:32`。

**根因链(源码 + 反汇编坐实)**:
1. toolchain `bits/os_defines.h:62` 定义 `_GTHREAD_USE_MUTEX_INIT_FUNC` → `gthr-default.h:78-80` `#undef __GTHREAD_MUTEX_INIT` → `ext/concurrence.h:115-142` 的 `__mutex`(**每个 shared_ptr 控制块内嵌**)ctor 调 `pthread_mutex_init`、dtor 无条件调 `pthread_mutex_destroy`,两者**都忽略/无法感知 init 失败**。
2. 内部堆 `MaxAlloc < ~100 B` 时 init 失败(`malloc esp_pthread_mutex_t`→ENOMEM,或 `xSemaphoreCreateMutex`→EAGAIN;j.log MaxAlloc 32 直接坐实),而**失败路径不写 `*mutex`** → 成员保留 `new` 垃圾。
3. 控制块 `delete this` → `~__mutex` → `pthread_mutex_destroy(垃圾)`;垃圾 ≠ `0xFFFFFFFF`/`NULL` → 不走早退分支 → `lock_internal` 读 mux+4 → fault。
4. `pthread_mutex_init` 实际来自**预编译** `framework-arduinoespressif32-libs/esp32c61/lib/libpthread.a(pthread.c.o)`(firmware.map:151027,`.pio` 内无 pthread.c.o)→ 原「patch framework-espidf pthread.c 加裁决日志」方案**无效**(源码不参与编译),改为直接修复 + 回归复现裁决。

**修复 F2(静态初始化,首选方案)**:`scripts/patch_gthr_static_mutex.py`(挂在 `platformio.ini` 的 `pre:` 列表)注释掉 toolchain 全部 `os_defines.h` 副本中的 `_GTHREAD_USE_MUTEX_INIT_FUNC`(幂等、上游行文本变化即告警跳过):`__GTHREAD_MUTEX_INIT`(=`PTHREAD_MUTEX_INITIALIZER`,`pthread_mutex_t` 为 `unsigned int` → 合法常量表达式,`std_mutex.h` constexpr 路径编译无风险)保持定义 → 控制块 `__mutex` 类内常量初始化且**不再声明 dtor**,我们的 TU 永不触达 `pthread_mutex_destroy`;`lock()` → `pthread_mutex_lock` → `pthread_mutex_init_if_static`(`pthread.c:724-729`)按哨兵值懒初始化。附带收益:每个控制块省 `malloc(8B)` + ~90 B 内部堆 `xSemaphoreCreateMutex` —— 正是 WiFi 连接时的分配高峰。混编风险(预编译归档 TUs 仍动态 init)最坏为有界泄漏,非崩溃;destroying `0xFFFFFFFF` 早退返回 0,跨界安全。

**验证**:
1. 反汇编:`jal pthread_mutex_init` 站点 **10 → 2**(`init_if_static` 内部懒初始化 + 预编译 libstdc++ 全局构造,均良性);**`pthread_mutex_destroy` 已被 `--gc-sections` 整体移出镜像(0 引用)** → 崩溃函数在固件中不存在;Flash −1,150 B。
2. 构建 gate:`pio run -e onepage` SUCCESS、单测 **231/231**、`pio check` PASSED。
3. 设备回归:**8 次 WiFi 连接**(设置页 ×5 含断开-扫描-重连循环 + 文件传输自动连接 ×3)全部成功,内部堆压到 `Min Free 2550 / MaxAlloc 2292`(与崩溃报告同一压力带),**0 panic、0 异常复位**;修复前同场景 3/3 崩溃。

**运维注意**:SCons 依赖扫描不跟踪 toolchain `-isystem` 头,改 `os_defines.h` 后增量构建和 `.cache`(`build_cache_dir = .cache`)命中的是**旧对象** —— 改动后必须 `pio run -e onepage -t clean && rm -rf .cache && pio run -e onepage` 全量重建(否则 `jal` 站点数不变、白测)。

**顺带诊断(喂给遗留项「文件传输界面 Back 键退出失效」)**:`CrossPointWebServerActivity.cpp:355` 在 500 次 `handleClient` 紧循环内每 64 次调 `mappedInput.update()`,而 `InputManager.cpp:100-102` 的 `update()` 开头**先清 `pressedEvents`** → 按下边沿在 `:357` 检查前被抹掉。串口注入必中(注入发生在 activity loop 之前),硬件按键取决于落点时机 —— 与「Back 偶发/必现失效」现象一致。

### 10.4 成本估算

| `/tools/invoke` 出厂硬拒名单:`exec`/`spawn`/`fs_*`/`cron`/`gateway`/`sessions_*` 等(策略可加) | gateway 文档 Auth/deny 矩阵 |
| Agent 轮次(`chat/completions`)内部工具策略不受 HTTP deny 限制;**本机已实测工具轮**:定闹钟 → `tool: automations` → cron added → 10.6 s 全链路 | port-plan §实测行 |
| 设备无通用 POST helper;`SttClient`(esp_http_client + TLS 前置 + SSE)是 POST 先例模板 | [SttClient.h:8-32](../lib/voice/SttClient.h) |

**两条候选路径**:
1. **`POST /tools/invoke`**(确定性、结构化 JSON、单工具、快):适合读取型工具;受 deny list 与 `tools.allow` 策略约束,须实测你实例上哪些工具可打。
2. **`POST /v1/chat/completions`**(OpenAI 兼容,一条固定提示词要结构化摘要):能力最全(走 agent 全策略,天气/待办 skill 只要实例已装就能用),但秒级延迟 + token 成本 + 回复需解析(要求模型回 JSON,限长)。
3. 兜底:不装 skill/工具被拒 → 状态文案「未配置」(§4.3 分级已有)。

**约束**:两条都是 POST → §10.3 ETag 行改为大概率不适用;超时 3/6/10 s 与堆 55 KB TLS 门槛照旧。

### 11.4 提醒 vs 省电:代码事实 + 业界惯例(决策④)

**本机事实**:
- 深睡唯一唤醒源 = 电源键 GPIO(`esp_deep_sleep_enable_gpio_wakeup`,[HalPowerManager.cpp:117](../lib/hal/HalPowerManager.cpp));**无 timer 唤醒**;唤醒 = 冷启动全流程([main.cpp:414-437](../src/main.cpp));无操作 10 min 自动睡([main.cpp:701-703](../src/main.cpp))。
- 无推送通道可用:WS 仅活动存活期在线,非 chat 帧一律 `Ignored`([OpenClawChat.cpp:326-331](../lib/OpenClaw/OpenClawChat.cpp)),port-plan 已裁 cron/widgets(`voice-openclaw-port-plan.md:349`);全库无既有提醒机制(grep 无 AI-08 代码,仅规划)。

**业界两类模式**:
1. **墨水屏 IoT 仪表盘**:深睡 + RTC timer 定时唤醒 → 联网取数 → 刷屏 → 回睡(~150 µA 睡眠电流,每次唤醒数秒 @~100 mA)。适合"看板",**刷新频率直接换算电池**。
2. **电子阅读器(Kobo/Kindle)**:**睡中零提醒**——不主动唤醒、不推送;内容在**用户下次自己唤醒时**呈现(待办/状态显示在开机首屏属于"零功耗提醒")。手机式推送需 Wi-Fi 常开 → 正撞 SCOPE Out-of-Scope「后台 Wi-Fi 任务」([SCOPE.md:42](../SCOPE.md))。

**结论:不相悖**,前提是提醒=被动而非主动:
- **模式 A(零成本,推荐 v1)**:每次唤醒(必是冷启动到 Home)即在工作台/首屏看到缓存待办与过期提醒——唤醒路径零改动。
- **模式 B(增量,推荐 v1)**:连接期刷新——用户打开工作台/AI 助手/任何联网活动时顺带同步,提醒数据随连接更新;无后台轮询,符合 PRD §6.1 与 SCOPE。
- **模式 C(定时唤醒主动提醒,缓办 opt-in)**:新增 `esp_deep_sleep_enable_timer_wakeup` + 每次唤醒冷启动 + 可能全网刷新 → 续航显著劣化,与 e-reader 预期相悖;若未来做,**默认关、设置项显式开启**,并给出频率档(如每日 1/3/6 次)。**裁定(§11.5-D2):必须事件驱动**——仅当存在未到期待办才武装 timer、醒后只画一行即回睡、全程无射频;轮询式定时醒已否决。

### 11.5 第一性原理裁定(2026-09-30,取代原提案)

**公理**(从产品与硬件本质导出;业界惯例仅作旁证不作依据):
- **P1 产品公理**:本机存在理由 = 深度阅读。条目成立条件 = 来源唯一性(手机上拿不到或更慢)× 对「本次阅读会话」决策的相关性。
- **P2 税负公理**:每个条目 = 渲染 + i18n + 状态机 + 同步 + 布局空间的永久税;屏幕与复杂度是本机最贵资源。
- **P3 射频公理**:睡眠 = 射频关(唯一唤醒源=电源键,醒即冷启动);主动触达必付唤醒代价;e-ink 双稳态 ⇒ 保持零功耗、更新画面才耗能。
- **P4 完整性公理**:错误默认值造成的静默数据污染(时区 → 聊天日界串天)不可接受,优先于便利。
- **P5 契约公理**:不为未观测的失败预写分支;接口契约(我们定义的 JSON)优先于依赖会漂移的外部能力面(工具名/schema);设备已验证代码模式(SttClient POST)是最低风险基座。

**裁定表**:

| # | 问题 | 裁定 | 第一性依据 |
|---|---|---|---|
